## 一、最要紧的三件事（直接影响结论可信度）

### 1. 全库 `description` 为空 → 文本分析模块实际是空转

实测 `data/boss_jobs.csv`：**8274/8274 行 description 均为空**。抽查原始批次 JSON，
`with jd: 0`（75 条全无 JD）。

原因链：`batch_crawl.py:203` 与 `smart_crawl.py:1087`（`run_one_query`）的抓取命令都写死 `--no-detail`，
`crawl_and_import.py:108` 的 `--details` 默认 0，所以**归档里从来就没有 JD**，
自然转换不出 description。

影响：

- `app.py:294 keyword_counts()` 只能从 `skills` 取词 → "职位文本高频词"图实际是第二张技能图；
- README「四、功能一览」里的**文本分析 / 词云**属于 README 有、数据无；
- 论文里若写了"基于 JD 的文本挖掘"，数据层面立不住。

建议：要么在抽样策略里对**每个岗位族挑 5-10 条**抓 JD（成本可控，词云够用），
要么把 UI 文案改成"技能词频"，不要让功能名和实际数据错位。

### 2. 125 家公司的 company 是"某知名电子商务公司"这类脱敏名

实测：`company` 以"某"开头的有 **125 条**。这是猎头/匿名招聘职位的 `boss_name`。

另外 `merge_jobs.py:126` 只用 `boss_name`，而 `boss_import.py:205` 是
`detail.company or boss_name`。两个脚本写同一个输出 `data/boss_jobs.csv`
（两者 `DEFAULT_OUTPUT` 都指向它），谁最后跑谁说了算 —— 这是"同名但不同口径"的隐患。

建议：
- 统一到 `boss_import.convert_batch` 的口径（详情公司名优先），merge 也要带详情；
- 在 UI/导出里把脱敏公司标记为「匿名企业」，或作为过滤维度，别让"热门企业榜"被这些名字污染。

### 3. 薪资离群值与"数据源三份不一致"

实测薪资分布：p50=7000，p99=35000，但 **min=100，max=250000**；
`salary_low < 2000` 有 **46 条**（多为日薪/实习折算或纯误抓，如
`('高级小程序开发工程师（技术主导）','福州',500,20000)`），
`salary_low ≥ 50000` 有 174 条，其中 2 条像"年薪当月薪"（250000-260000）。

这些值会直接抬高 `avg_salary`（看板首屏卡片）和薪资分布图。

同时存在**三个互相矛盾的事实源**：
`data/boss_jobs.csv`（8274 行）、`data/crawl_report.md`（独立岗位 8294）、
`data/crawl_ledger.json`（combos.raw 合计 2649）。没有任何一处能说明差异从何而来。

建议：
- `boss_import.parse_salary` 增加**量纲校验**：日薪/时薪必须带 `/天|/时` 才折算；
  月薪低于 2000 或高于 20 万单独进 quarantine 报告，不静默进主表；
- 增加 `--verify` 子命令：CSV 行数 vs 归档 job_id 数 vs 账本新增数三方对账，
  数字不一致就报错。这是论文"数据可信度"一节最便宜的加分项。

## 二、工程结构：脚本太多、职责重叠、没有包

现在根目录 9 个平铺脚本，互相 import 靠隐式同目录（`batch_crawl.py:30` 手写
`sys.path.insert`），`analyze_yield.py` 把同一个归档目录**完整扫了 3 遍**
（28、61、78 行三处 `rglob` 循环，`city_records` 那段把第一次的结果完全作废）。

`smart_crawl.py` 1244 行，其中 `Scheduler` 类占 381-645 行（约 265 行），
调度策略、切片、账本、报告混在一个文件里。

建议改成一个可安装的包（保持向后兼容的 shim 脚本）：

```text
jobanal/__init__.py
        config.py        # 城市/岗位族/限流/路径常量集中，替换散落的字面量
        parsing.py       # parse_salary/city/education/experience（唯一口径）
        importers.py     # boss_import + merge_jobs + consolidate_archive 合一
        store.py         # SQLite 落库（见下）
        scheduler.py     # smart_crawl 的调度与账本
        web.py           # Flask 应用工厂
cli.py                   # 一个入口：jobanal crawl/import/verify/report/web
```

另外 `requirements.txt` 全量钉死（`Flask==3.0.3`/`pandas==2.2.3`）对毕业设计交付是好事，
但应额外提供 `requirements-dev.txt` 与 `constraints.txt`，避免 Python 3.13/3.14 上
装不了 pandas 时整个项目起不来（本次评审环境就复现了这一点）。

## 三、数据层：建议从"每次重写 CSV"换成 SQLite

当前 `boss_import.py` / `merge_jobs.py` / `consolidate_archive.py` **都是全量重写** CSV
（AGENTS.md 自己也强调了这点），带来三个后果：

1. **job_id 不稳定**：`app.py:175` 用 `df["job_id"] = range(1, len(df)+1)` 生成行号，
   一旦重跑导入，同一岗位的 job_id 整体漂移；`/api/jobs/<id>` 返回的内容也随之变化，
   分享出去的链接失效。
2. **丢掉了时间维度**：归档目录名带批次时间戳，`data/crawl_ledger.json` 有 8 次 run 记录，
   但 CSV 里**没有任何采集时间字段**，所以"某技能需求逐月变化 / 岗位量趋势"这类
   整个系统最有说服力的分析，现在做不出来。
3. **无法增量**：8274 条每次全量清洗，归档已有 20MB+ 且只增不减。

建议：`data/jobs.db`（SQLite，标准库 sqlite3，零依赖），表 `jobs(job_id PRIMARY KEY,
title, company, city, salary_low, ..., first_seen, last_seen, source_batch)`，
`job_postings(job_id, scraped_at, raw_json)` 存快照。收益：
稳定 ID（用 BOSS 的 `job_id` 而不是行号）、增量 upsert、可做时间序列、
导出 CSV 变成查询而非重写。app.py 只需把 `load_data()` 换成一次 SQL 查询 + 缓存。

## 八、这套东西真正的差异化机会

现在它停在"抓下来 → 存 CSV → 出几张静态分布图"，这类系统网上很多、区分度低。
但你手上其实握着**别人没有的资产**：371 城 × 20 岗位族的调度账本、多批次时间戳归档、
收益率分析工具。

把存储换成 SQLite 之后，下面三件事几乎不需要新数据就能做出来：

1. **需求趋势**：同一技能/岗位族跨批次的数量变化曲线（"大模型算法岗 9 月环比 +X%"）。
2. **采集质量报告**：哪些城市/关键词是"白抓"（收益率低）、哪些维度还是空白，
   账本里已经有 `runs[].new_jobs / raw` 全部原料。
3. **同岗多快照比价**：`merge_jobs.pick_best` 已经实现了"同一 job_id 多份快照取最全"，
   反过来就能做"同一岗位薪资随时间变化 / 挂岗时长"。

这三张图一上，系统从"岗位分布看板"变成"招聘市场监测系统"，论文的"创新点"
和"不足与展望"两节都能直接落地。

# 附录 A：`smart_crawl.py` 专项深挖（1243 行 + 与其 fork 的 scraper 交叉验证）

`smart_crawl.py` 是全仓最复杂的一块，单独再做了一轮针对调度逻辑、账本一致性与
scraper 契约的深挖。以下按"是否已复核"标注。

## A0 真实数据流（澄清）

它自己不抓数据，是**覆盖度驱动的调度器**：规划 (城市 × 工种族 × 可选经验/学历切片)
组合 → 每个组合 fork 一次 `scraper/scripts/boss_cdp_raw.py` → 归档到
`抓取结果/smart_<日期_时分>/boss_jobs_<城市>_<族>_<秒>.json`。
跨运行记忆只有 `data/crawl_ledger.json`（v2），加上对归档目录的全量重扫 `scan_archive()`。
`job_id` 由 scraper 用 `md5(job_link or title)[:16]` 生成，所以**跨批次稳定** ——
这一点比 CSV 里用行号当 ID 强得多（见正文第三节）。

## A3 smart_crawl 的改造优先级（与正文 P0 并列）

1. **`saturated` 判定改成"有结果才允许拉黑"**：`raw == 0` 或文件缺失一律记 `failed` 并允许重试

4. 基础查询后**立刻落盘 `truncated`**（把 `:1191` 前置到 `:1146` 附近），消除僵尸组合。
